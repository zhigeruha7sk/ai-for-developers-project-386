Cервис, где владелец публикует доступное время для встреч, а другой пользователь выбирает свободный слот и записывается на звонок.
В проекте нет авторизации, личных кабинетов и интеграций с внешними календарями.
Владелец календаря в приложении один и задан заранее. 
Он заводит типы встреч, у каждого есть название, описание и длительность, и смотрит список предстоящих встреч всех типов. 
Гость заходит без регистрации, выбирает тип встречи, открывает календарь на ближайшие 14 дней и записывается на свободный слот. 
Слот длится столько, сколько выбранный тип встречи. Одно и то же время нельзя занять дважды, даже разными типами встреч.
Окно записи занимает 14 календарных дней и сдвигается с течением времени. 
Начало с сегодняшнего, часы работы владельца с 09:00 до 18:00 (с 13:00 по 14:00 обед) и часовой пояс Алматы(Казахстан).
Длительность слота совпадает с длительностью типа встречи, шаг доступных стартов тоже фиксируется в спецификации. 
Пересечение интервалов запрещено, включая частичное наложение разных типов. 
Следующая встреча может начинаться в момент окончания предыдущей. 
Правила действуют и для двух запросов, пришедших одновременно.
Данные можно хранить в памяти процесса. В этом случае перезапуск сбрасывает записи.

Всего в приложении будет 4 страницы.

В левом верхнем углу логотип календаря и надпись Calendar В правом верхнем углу две кнопки (Записаться и Админка).
Верхняя срока с логотипом и кнопками должна быть на всех страницах.

Приложение на java spring boot.
Обязательная цепочка TypeSpec, OpenAPI и генератор SDK для языка фронтенда.
Клиентский SDK обязателен.
Тестов на функциональность здесь ещё нет, поэтому в CI достаточно одного дымового теста: приложение поднимается и отвечает. 
Задача шага в том, чтобы прогон тестов и линтера работал автоматически до появления первой фичи.
Программа запуска тестов находит тесты, выполняет их и сообщает результат. Для Java JUnit с задачей сборщика.
GitHub Actions запускает выбранную вами команду на машине CI. 
В этом шаге достаточно одного дымового теста, который проверяет запуск приложения и успешный ответ на запрос. 
Проверки полного сценария бронирования появятся вместе с функциональностью.
Нужно использовать mise для всего окружения разработки. 
В mise.toml фиксируются версии инструментов, переменные окружения, задачи установки, запуска, сборки и проверок. 
Хуки mise позволяют запускать задачи при установке инструментов или входе в проект. 
Git-хуки рекомендуем настроить через hk, установленный с помощью mise, и вызывать из них те же проверки. 
Фоновые серверы и сервисы разработки описываются через daemons mise, чтобы агент мог запускать, останавливать их и смотреть состояние. 
Для daemons включите experimental = true в разделе [settings] и зафиксируйте версию pitchfork, который управляет процессами.
Соберите проверки в одну задачу, например mise run check. 
Сейчас она запускает линтер, проверку типов, если она есть в стеке, и дымовой тест. 
GitHub Actions вызывает эту же команду. По мере разработки в неё добавляются остальные тесты.
Создай формат Conventional Commits (feat:, fix: и так далее) и запишите правило в AGENTS.md. 
Автоматические релизы через release-please подключим на шаге реализации после первой функции. На этапе каркаса их настраивать не нужно.

Требования.
Бекенд и фронтенд запускаются локально.
В проекте есть команды запуска тестов и линтера.
Одна команда запускает все текущие проверки локально и в GitHub Actions на каждый push, прогон зелёный. Версии инструментов зафиксированы в проекте.
Коммиты идут по Conventional Commits.
В корне репозитория есть AGENTS.md с командами запуска, тестов и линтера и с правилом про формат коммитов.
AGENTS.md короткий и без противоречивых правил. В нём только команды, устройство проекта и правила, которые из кода не читаются.
